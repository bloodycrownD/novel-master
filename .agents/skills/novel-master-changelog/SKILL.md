# CHANGELOG 撰写

面向用户的更新说明，用户在 GitHub Release、桌面端关于页、移动端更新弹窗看到的内容。写 changelog 时**站在用户视角**，不暴露内部实现细节。

## 输入

从下列来源汇总本批改动（用户会指定其中部分或全部）：

- 当前迭代/PRD/SPEC 路径（`docs/Iterations/<name>/`）
- 工作区 diff / commit 历史（`git --no-pager log --oneline <base>..HEAD`、`git --no-pager diff <base>..HEAD --stat`）
- CR fix-spec（`docs/Iterations/<name>/cr-fix-spec.md`）——但 **fix-spec 是内部实现质量记录，不是用户可见 changelog 条目的来源**
- fix-spec 仅用于理解"这条修复到底修了什么用户可感知的问题"

**禁止**把 fix-spec 的 CR 编号、内部术语（CR-1、scope、P0/P1、C-orch 等）写进 changelog。用户看不到这些编号。

## 分类规范

[CHANGELOG.md](../../../CHANGELOG.md) 使用 Keep a Changelog 格式，分四类：

| 分类 | 含义 | 判断标准 |
|------|------|----------|
| **新增** | 用户获得了之前没有的能力 | "现在可以做 X 了" |
| **修复** | 修复了用户实际遇到 / 可感知的 bug | "之前 X 不工作 / 报错 / 行为异常，现在修好了" |
| **变更** | 用户可感知的行为或界面变化 | "X 的表现 / 展示变了"（不是 bug，是刻意调整） |
| **维护** | 内部重构、类型收敛、死代码清理、架构调整等 | "代码层面做了 X 整理"——对用户行为无直接影响，但记录让开发者 / 维护者知道改了什么 |

## 核心原则

### 1. 一个功能只在一个分类出现

不要把同一个功能的"主功能"写在新增、"实现细节"写在变更、"内部收尾"写在维护。用户看到的是**一个完整的功能**，不是三段拆开的流水账。维护段写的是**独立的内部改动**（如纯重构、死代码清理），不是某个用户可见功能的实现细节。

> ❌ 新增：token usage 持久化（含回填）
> ❌ 变更：backfill 逻辑收敛到 core
> ❌ 维护：LlmTokenUsage 类型收敛
>
> ✅ 新增：token usage 持久化（一句话讲完"存了什么 + 回填兜底"）
> ✅ 维护：删除事件编排器 / 旧 migration 注册表清理（独立的内部重构，不是某个功能的实现细节）

**判断方法**：写完一条后问自己"这条和上面那条是同一个东西吗？"——如果是，合并。

### 2. 不要把开发过程中引入又修复的 bug 写进「修复」

CR / 实现过程中发现并修复的 bug，如果用户从未在正式版本体验过（因为同一批改动引入 + 修复），**不写进修复**——用户看到"修了 X"会以为之前有这个问题。

> ❌ 修复：streamRegistry 多步重进重复渲染（本轮 CR 引入 + 修复，用户没体验过）
>
> ✅ 修复：子会话退出再进入消息消失（用户实际遇到的 Bug3，带一句"并补齐多步重进与并发场景的稳定性"即可）

### 3. 内部术语转人话

用户不在乎 CR 编号、scope、P0/P1、模块路径、类型名。把技术实现翻译成用户能懂的"做了什么 / 修了什么"。

> ❌ 修复（Bug3 / CR-2）：streamRegistry 无 per-step reset，EVENT_AGENT_STEP_COMMITTED 后未调 reset 导致重复推送
>
> ✅ 修复：子会话在流式输出中退出再进入时消息丢失——现已支持流式内容缓存与恢复

### 4. 面向"做了什么"，不是"怎么做的"

条目描述结果和用户价值，不暴露实现路径。实现细节留在 commit message / spec / fix-spec 里。

> ❌ 新增：token usage 持久化（用 resolvePromptTokensWithBackfill helper 实现 cache miss 回填）
>
> ✅ 新增：token usage 持久化（不提 helper 名）
> ✅ 维护：两端 chat-prompt-tokens.service 的 cache miss 回填逻辑收敛为 core 共享 helper（独立的内部收敛）

## 撰写流程

1. **汇总改动**：按"输入"节的来源收集本批改动清单
2. **分类**：判断每条改动属于哪一类——用户可见的功能 / 修复 / 变更，还是内部重构 / 清理（维护）
3. **归并**：同一功能的子项合并成一条
4. **分类**：每条按"分类规范"表归入唯一一类
5. **翻译**：每条转成人话（用户视角，结果导向）
6. **写入**：追加到 `## [Unreleased]` 段（发版时由 publish skill 挪到具体版本号）

## 校对清单（写完逐项过）

- [ ] **无重复**：同一功能 / 同一用户可感知的行为只在一个分类出现一次
- [ ] **无内部细节**：没有 CR 编号、scope、P0/P1、类型名、模块路径、helper 名
- [ ] **无过程 bug**：开发过程中引入又修复的 bug 不在「修复」段（用户没体验过的）
- [ ] **维护段覆盖**：内部重构 / 收敛 / 死代码清理有记录在维护段（独立的内部改动才写，不是某功能的实现细节）
- [ ] **面向用户**：每条都是"用户能看到 / 体验到什么"，不是"代码改了哪些文件"
- [ ] **无错别字**：通读一遍，尤其是技术术语（锚点 ≠ 锦点、consistent ≠ 一致性）
- [ ] **措辞简洁**：一条尽量一两句话讲完，不铺陈实现

## 格式参考

```markdown
- **简短标题**（可选端标注）：一句话描述用户可感知的变化——补充一句必要上下文
```

参考既有条目（如 `## [1.4.20]` 段），保持措辞风格一致。粗体标题概括要点，破折号后补充上下文。
