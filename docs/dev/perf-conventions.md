# 性能约定

这套约定不是说要把代码拧到极致快，而是把「明显在热点路径上重复劳动、又一眼能看出来纯函数」的情况统一收口，免得每个模块各写各的缓存、各踩各的坑。

## AgentRunner 主循环的纯函数必须 memoize

`AgentRunner` 的主循环在一个 turn 里会反复跑同样的计算：同一份 SQL 模板要被解析好几遍、同一个 `test` 表达式要在每一轮 `foreach` 迭代和每一个 `when` 分支上重新求值、同一条逻辑路径要在多个工具调用里反复规范化。这些函数有个共同点——输入相同，输出必然相同，而且不依赖任何外部可变状态。这正是 memoize 最该发力的地方，所以约定：凡是挂在主循环热点上的纯函数，一律套上 `@/common/memoize.js` 暴露的 `memoize`，不要让它们在同一个 turn 里被反复重算。

具体的做法已经在代码里落地了。`SqlTemplateParser.parse` 内部按模板字符串原文缓存了 AST，同一份模板第二次进来直接复用上次的解析结果；`expression.ts` 里 `new Function` 编译出来的函数也按规范化后的表达式体做了缓存，因为 `new Function` 在 V8 里会触发即时编译，单次开销不小，反复编译纯属浪费；`vfs-path-mapper.ts` 则把原本一条调用链里串了多次的 `normalizePath` 收敛成一次，避免同一条路径被规范化好几遍。这几个是范例，后续往主循环上加新的纯函数时，照着这个路子走就行。

不过 memoize 不是万能药，套之前得先确认函数确实是纯的。它不能依赖任何会变的闭包变量、不能读外部可变状态，更不能有副作用——否则缓存命中时会跳过本应执行的副作用，行为就会偷偷错掉。另外缓存的生命周期也要想清楚：单参数里对象 key 走 `WeakMap`，对象被回收后条目自动消失，不用担心内存泄漏；原始值 key 和多参数缓存树里的中间层走的是普通 `Map`，所以只适合 key 集合有限、数量可控的场景（比如固定的一批模板字符串、表达式文本），千万别拿用户自由输入的长字符串当 key 无限往里塞。拿不准的时候就别套，先把函数理清楚再说。
