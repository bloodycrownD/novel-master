# 常驻保活通知（resident-keepalive-notification）PRD

## 背景

真机排查（荣耀 DSLDU20407006179，EMUI）定案：保活通知走 notifee 前台服务（ForegroundService），EMUI 对「距上次前台服务停止超过约 3 分钟后启动的前台服务通知」执行 **10 秒延迟展示**（系统日志 `delay foreground service ntf`：通知已入队但不展示，10 秒后系统放行才对用户可见；3 分钟冷却窗口内的连续启动不受影响）。app 侧链路本身健康（点发送 → 通知入队 632-670ms），但「随 run 启停」的生命周期让用户最常见路径——打开 app 后的第一条消息——必然撞上 10 秒压制，表现为「发送后切到桌面拉状态栏，『生成中』10 几秒后才出现」。

对策（用户拍板）：把前台服务通知从「随 run 启停」改为「app 启动即常驻」——启动时刻用户正在看 app，压制发生在视线之外；此后发送消息只是**更新一条已展示的通知**（已展示通知的内容更新不受压制，实测毫秒级生效），彻底绕开 10 秒窗口。

现状（init-busy-yield-2026-09 交付后）：`agent-finished-notification.ts` 的 keepalive 期望态（keepAliveDesired）完全由 run 生命周期驱动（受理即起、全部收尾即停）；「消息通知」开关（`messageNotification`，默认开）在每次 run 受理时查询；权限申请时机钉死为「首次发起 run 且开关为开」；通知内容无空闲态文案。

## 目标（含成功指标）

| 指标 | 现状 | 目标 |
|------|------|------|
| 常驻通知出现时机 | 仅生成期间（且首启被 EMUI 压 10 秒） | 开关开启时进 app 即常驻（空闲态文案），首启 10 秒压制发生在 app 内、用户无感 |
| 点发送 → 「正在生成」对用户可见 | 冷启动首条 10+ 秒 | **≤2 秒**（已展示通知的原位内容更新，无系统压制） |
| run 结束 | 通知消失、服务停止 | 通知回「novel master · 空闲」，服务保持 |
| 开关默认值 | 开 | **关**（默认无任何通知行为） |
| 通知权限申请 | 首次发送时弹系统弹窗 | 开关开启时申请 + 设置页手动按钮（状态展示 + 永久拒绝跳系统设置） |

## 用户与场景

- mobile（Android）全部用户；desktop 无通知功能，不在范围。
- 场景 1：用户打开 app 浏览/编辑（未发送）——状态栏常驻「novel master · 空闲」，表示 app 活跃与后台保活能力就绪。
- 场景 2：发送消息——常驻通知原位切换为「正在生成 · 会话名」，用户切到桌面拉状态栏立即可见（不再等 10 秒）。
- 场景 3：生成结束用户已离开 app——常驻通知回空闲态，同时普通「生成完成」通知照常提醒（现状能力保留）。
- 场景 4：用户不想看到任何通知——设置里关掉「消息通知」开关，常驻通知与完成提醒全部消失（默认即此状态）。

## 范围

### 包含范围

- keepalive 生命周期改常驻：开关开启时 app 启动即启动前台服务通知（空闲文案），run 受理/收尾只更新内容、不再启停服务；开关关闭时立即停（含 run 进行中）。
- 空闲态通知文案「novel master · 空闲」。
- 「消息通知」开关默认值改关；设置页副标题两态文案改写。
- 通知权限申请时机挪到「开关开启」；聊天配置页新增「通知权限」行（状态展示 + 手动申请，永久拒绝时跳系统通知设置）。
- 完成通知（普通通知）行为保持现状。
- 对 init-busy-yield PRD 验收口径的影响声明（见风险与待确认项）。

### 不包含范围

- desktop 端（无对应功能）。
- iOS 通知能力承诺（现状 iOS 不起服务不发通知，维持）。
- 前台服务 serviceType 更换或 EMUI 白名单/豁免调研（用户拍板接受 dataSync 6 小时限额现状）。
- 「生成中」通知的交互增强（进度、展开等）。

## 核心需求（3-7 条）

1. **常驻生命周期**：开关开启 → app 启动（runtime 装配完成）即启动常驻前台服务通知，内容「novel master · 空闲」；杀掉 app 通知消失；开关关闭立即停服务撤通知（含生成进行中——run 继续执行，仅失去保活）。
2. **生成状态切换**：run 受理时通知原位更新为「正在生成 · 会话名」（多会话聚合文案保持现状逻辑）；全部 run 结束回「novel master · 空闲」，服务不停。开关关闭时的 run 受理不产生任何通知刷新。
3. **默认关**：全新安装默认关闭，无常驻通知、无完成提醒；开关语义为「总开关」（开 = 常驻保活 + 完成提醒；关 = 全部无）。
4. **权限申请前移**：开关从关闭切到开启时触发一次系统权限申请（Android 13+）；权限未授权时开关行为不降级（服务照常起，通知不可见——维持现状口径），设置页状态引导用户补授权。
5. **手动权限入口**：聊天配置页「消息通知」下方新增「通知权限」行——展示当前权限状态（已授权 / 未授权 / 已被系统拒绝），点击行为：未授权 → 弹系统申请；永久拒绝 → 跳系统通知设置页。
6. **完成通知不变**：run 结束且 app 在后台时的普通通知（生成完成/失败、点按直达会话）行为与现状一致。

## 验收标准

- **GWT-1（进 app 常驻）**：Given 开关开启且通知权限已授权，When 冷启动 app 进入主界面并等待初始化完成，Then 常驻通知以「novel master · 空闲」出现在通知栏（logcat `onNotificationPosted` 双证；允许 EMUI 首启 10 秒压制发生在 app 内）。
- **GWT-2（生成即时可见）**：Given 常驻通知已展示（空闲态），When 在 app 内发送消息并立即切到桌面拉下状态栏，Then 通知已显示「正在生成 · 会话名」，点发送 → 内容可见 ≤2 秒（logcat 无新增 `delay foreground service ntf` 行）。
- **GWT-3（回空闲不停服）**：When 最后一个 run 结束，Then 通知内容回「novel master · 空闲」且前台服务不停止（系统服务日志无 stopForegroundService）。
- **GWT-4（开关即时性）**：When 生成进行中把开关切到关闭，Then 常驻通知立即消失、服务停止，run 继续执行不受影响；When 切回开启，Then 常驻通知立即恢复（空闲或生成态与当前实际一致）。
- **GWT-5（默认关）**：Given 全新安装（或清除数据）未改过设置，When 启动 app 并发送消息，Then 无常驻通知、无完成提醒；设置页开关显示关闭。
- **GWT-6（权限链路）**：When 开关从关切到开且从未申请过权限，Then 弹系统权限申请；权限行显示当前状态；永久拒绝后点击权限行跳转系统通知设置页。
- **GWT-7（完成通知保留）**：Given 开关开启、run 结束时 app 在后台，Then 收到普通「生成完成」通知（与现状一致，毫秒级无压制）。
- **GWT-8（杀 app 消失）**：When 从最近任务划掉/强制停止 app，Then 常驻通知消失。

## 风险与待确认项

- **对在途迭代验收的影响（已拍板方向，落地时执行）**：init-busy-yield PRD 的 GWT-1/GWT-4 以「点发送 → 保活通知出现 ≤2s/≤1s」为锚点——常驻化后锚点变为「内容更新」时序，原验收口径由本需求 GWT-2 接替；旧 PRD 作为历史文档不回改，验收以本 PRD 为准。
- **Android 14+ dataSync 前台服务约 6 小时系统限额**（用户已拍板接受）：常驻单次最长约 6 小时，超时系统按外力关闭处理（通知消失、下次打开重新常驻）；不为此更换 serviceType。
- **runtime retry/dispose 闪断**：Manager.dispose 现状无条件全停服务，retry 重建后由桥装配重新拉起——窗口内通知消失再出现（秒级），接受。
- **EMUI 首启 10 秒压制**：发生在「进 app 时刻」，用户正在 app 内无感知；但「启动后 10 秒内快速发送并切桌面」的极端场景仍要等首启压制结束（与现状持平，不更差）。
- **权限永久拒绝通路为新增代码**：`notifee.getNotificationSettings` / `openNotificationSettings` 仓库无先例，需在 spec 中定义状态判定与跳转细节。
