# 预览提示词 workplace 压缩后刷新 + 预览行号移除 PRD

## 背景

预览提示词页（mobile 入口：会话抽屉菜单「查看提示词」/ 会话详情页卡片「查看提示词」；desktop 入口：会话详情抽屉「查看提示词」/ 会话面板「提示词」Tab）在 2026-10 的 `ui-prompt-fixes-2026-10` 迭代中重构为「轮聚合卡片流」形态。本轮处理该页暴露的两处问题：

**问题一：压缩上下文后 workplace 块不刷新。** 用户压缩上下文后查看预览提示词，`<workplace>` 块停留在旧内容（缺少 agent 后续新建的文件、正文为旧版），必须手动调整一次工作区规则（目录规则）后才刷新。探索定位的根因：workplace 块由会话级两份缓存拼装——`rule_snapshot`（文件清单快照）与 `file_cache`（展示正文缓存）；清单快照在会话首次组装后即冻结（agent 用 write 新建文件不会重写清单，新文件永不进前缀），正文缓存命中时不校验文件改动（edit 工具、编辑器保存均不失效）；而压缩按 2026-09-29 用户拍板「压缩不清 rule_snapshot/file_cache」不清这两份缓存。「手动调整工作区规则」触发的 `refreshRuleSnapshot`（重写清单 + 清正文缓存）是当前唯一强制刷新入口——这正是「调一次规则就好」的机制。即：病灶是两份缓存的长期陈旧，压缩是用户发现它的时机。

**问题二：预览页 Assistant/user 轮内容正文带行号。** 查证结论：预览 UI 层没有任何加行号的代码；行号是提示词 wire 正文自带的格式——workplace 文件块、user 消息附件正文、assistant 轮 read 工具结果，发给模型时就是「`1|内容`」形态（行号是模型定位行、执行编辑回填的依据，2026-07 即定型）。新预览页如实渲染了这份正文，行号才变得显眼。无任何迭代立项或拍板过「预览显示行号」。纯手打文本与 thinking 无行号。

## 目标（含成功指标）

1. 手动压缩上下文后，预览提示词的 workplace 块反映压缩时点的当前工作区。成功指标：agent 新建文件 → 手动压缩 → 打开预览提示词，新文件出现在 workplace 块且正文为最新，无需再手动调整工作区规则。
2. 预览提示词页各卡片正文不再显示行号前缀。成功指标：workplace 文件预览、附件正文、工具结果正文在预览页均无「`N|`」前缀，其余字符与原正文逐字一致。

## 用户与场景

- **长会话作者**：上下文接近阈值时手动压缩，随后打开「查看提示词」核对将发送给模型的内容，发现 workplace 块与实际工作区不符；当前只能通过手动调整一次工作区规则来强制刷新。
- **预览页阅读者**：点开轮卡/全屏详情阅读 Assistant/user 内容时，被「`1|`」「`     1|`」行号前缀干扰，认为行号并非其所要求的展示行为。

## 范围

### 包含范围
- 手动压缩入口完成后 workplace 清单与正文缓存的重算/失效机制（默认口径见核心需求 1）。
- 预览提示词页（双端）正文渲染剥离行号前缀（默认仅显示层，见核心需求 2）。
- 预览屏数据刷新时机补齐（压缩后进入/返回预览页能看到新内容）。
- 文档与注释对齐：`docs/apm/RULE.md` 压缩/导入/workplace 三条目、core 与 desktop 侧六处「压缩清两域」漂移注释（完整清单见 SPEC Step 10 七项），随新口径一并修正。
- 相关测试随口径更新（`run-compaction.test.ts`、desktop `compaction-handler.test.ts`、mobile 压缩编排测试、双端预览渲染测试；`refresh-rule-snapshot` 域口径未动，仅作回归面不改）。

### 不包含范围
- 不改变发给 LLM 的提示词 wire 格式（行号保留在发送内容中；若用户拍板改为 wire 去行号则另行立项评估工具链影响）。
- 不改 workplace 展示档规则（「全内容/文件名/文件头」）与目录规则引擎本身。
- 不改压缩锚定/消息可见性逻辑。
- 默认不做「缓存随文件变动全链路即时失效」的治本改造（write/edit/保存后 workplace 即时新鲜）——列为待确认备选。

## 核心需求（3-7 条）

1. **手动压缩后 workplace 完整刷新【默认口径，待确认】**：手动「压缩上下文」成功后，对该会话执行与「手动调整工作区规则」等价的刷新（重评估 `rule_snapshot` 清单 + 失效 `file_cache` 正文），下一次拼提示词（发送或预览）时 workplace 块反映当前工作区。此口径收窄 2026-09-29「压缩不清缓存」拍板至「自动压缩不清」。
2. **自动压缩维持不清缓存**：agent 回合中段触发的条件压缩不改变两份缓存，保住「回合内前缀冻结」（每 step 是前一步纯追加）与 provider 前缀缓存命中。若用户要求自动压缩也刷新，需另行评估前缀缓存失效代价（待确认项 2）。
3. **预览行号仅显示层移除【默认口径，待确认】**：双端预览提示词页的正文渲染（含就地展开预览卡、全屏详情/raw 视图）剥离「`行号|`」前缀（含 6 位右对齐空格填充形态）；发送给模型的提示词保持原样仍带行号。
4. **双端同构**：mobile 与 desktop 同步实施上述改动（默认，待确认项 3）。
5. **预览屏刷新时机**：压缩完成后，用户进入预览页（含从导航栈保活返回的场景）取到的是刷新后的 workplace 内容。
6. **文档对齐**：按最终口径同步修订 RULE.md 三条目与六处代码注释的「压缩清两域」表述，避免后续 CR/改动代理依据漂移文本误判（`repo-mega-cr-2026-10` CD-57 同类漂移先例）。

## 风险与待确认项

1. **【待确认】刷新口径**：默认「手动压缩后完整刷新（清单+正文）」；备选「只重算清单（正文缓存复用，更快但编辑过的正文可能仍旧）」「治本全链路失效（不限压缩时机，改动面最大）」。完整刷新的代价：压缩后下一次拼提示词需重读文件、略变慢（正是 2026-09-29 拍板当初要治的「压缩卡顿」，收窄至手动入口后影响可控）。
2. **【待确认】自动压缩是否刷新**：默认不刷新（护住回合内前缀冻结不变量）；若要求刷新，需评估 provider 前缀缓存失效与回合中段重评估链的代价。
3. **【待确认】行号口径**：默认「仅预览显示层隐藏，发送不变」（模型行定位能力不受影响）；备选「wire 去行号」（模型失去行号锚点，影响 read 续读与 edit/write 回填定位，风险大）、「默认隐藏 + 可切换」（保留所见即所发的核对能力）。隐藏后预览不再严格「所见即所发」（正文主体一致、仅行号差异）。
4. **【待确认】端范围**：默认双端同构；备选仅 mobile 或仅 desktop。
5. **风险**：mobile 预览屏当前仅在挂载时取数、不订阅压缩事件——压缩后从导航栈保活返回预览页可能仍显示旧数据，实现时需补焦点回流/事件订阅（核心需求 5 已纳入）。
6. **风险**：`run-compaction.test.ts` T-CC2/3/4 等既有测试锁定「压缩后两域必须仍在」，口径收窄后需按「手动入口清、自动入口不清」拆分断言，避免误伤置位/导入链路的既有用例。
