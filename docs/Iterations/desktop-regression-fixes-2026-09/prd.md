回归同时发现一批新问题，登记于本表。问题分两类编号：D-x 为用户可见的缺陷/体验问题，S-x 为系统性/工程卫生问题。

## 问题记录表

### D-1（必修）PreviewPane 空态 `setVersion` ReferenceError

- **现象**：`apps/desktop/renderer/layout/PreviewPane.tsx:139`，`loadFile` 的 `previewFile` 为空分支调用未声明的 `setVersion(undefined)`。冷启动、新建项目、新建会话时 DevTools console 抛 `ReferenceError: setVersion is not defined`。
- **影响评估**（已探明）：错误为 unhandled promise rejection，不进 error boundary、不炸组件树；预览/编辑/保存功能完全正常；唯一逻辑副作用是同分支的 `setFileMissing(false)` 被跳过，无可见 UI 影响。属「必抛但无害」的 console 污染。
- **根因**：v1.5.12 的 VFS 版本校验整体移除（commit 60af90b8）删除了 version state 声明及其它三处调用，唯独漏删空态分支这一行；同批 CR 修正手机端 FileEditorScreen 时注明「对齐 desktop PreviewPane」，实际 desktop 未对齐。
- **基准参照**：手机端 FileEditorScreen 当前无任何 version 语义，保存直写。删除该行即与手机端形态完全一致。
- **影响版本**：仅 v1.5.12（该 commit 仅被此 tag 包含）。

### D-2（必修·待拍板方向）发送失败反馈弱且双端口径不一

- **现状（桌面端）**：agent run 失败走双通道——composer 上方红字（经 formatUserError）+ toast（3.2 秒自动消失，内容为裸英文原文、未经格式化，与红字口径不一致）。无重试按钮、消息气泡无失败标记；事实上的续跑入口是空发送（composer 在末条为 user 消息时可空内容发送续跑），但无 UI 指引。
- **现状（手机端·基准）**：仅 composer 上方一行红字、英文原文透传，无 toast、无重试，该口径从未经迭代拍板。
- **问题实质**：英文原文（"fetch failed"）对用户不友好；错误原因链在 agent-runner 层即被截断（ECONNREFUSED 等深层原因丢失）；双端传输层文案不同源（桌面 undici "fetch failed" vs 手机 RN "Network request failed"）。
- **候选方向（待拍板）**：
  - A. 桌面向手机端对齐：砍 toast，仅留红字（最省事，实为降级）；
  - B. 双端统一中文可读文案（按错误类型映射：网络失败/API Key 未配置/超时等）；
  - C. B + 失败重试/续跑指引（toast actionLabel 或红字旁按钮，桌面 toast-bus 已支持 action 机制）。
- **拆分建议**：无论选哪个方向，此条拆为独立小 PRD（涉及双端时手机端部分再拆）。

### D-12（必修）SkillDetailView 未保存确认只拦截两条路径，侧导航切走静默丢弃编辑

- **现象（第四轮回归 464/465 截图实锤）**：编辑 SKILL.md 至脏状态（状态行「未保存（Ctrl+S 保存）」）后点设置侧导航切换到其它页签——无任何确认弹窗/toast，直接切走，编辑内容静默丢弃。
- **根因**：`guarded()` 只包了两条路径——切文件（L282 `guarded(() => setSelected(path))`）与「返回」按钮（L326 `guarded(() => nav.pop())`）；设置侧导航切换、关闭设置等路径不经过拦截。文件头注释自述「未保存离开（切文件 / 返回）时确认拦截」——实现与注释一致但覆盖不全。**补充（2026-09-08 spec 第 1 轮审查）**：`OPEN_SETTINGS_VIEW_EVENT` 编程式跳转（聊天侧技能面板「整理」/行点击触发）是第三条泄漏路径，其中行点击的 viewingSkillRef 覆写不卸载组件、直接静默丢脏编辑，一并纳入守卫（见 spec D-12 第四分发点）。
- **影响**：技能文件编辑到一半点侧导航是常见操作，脏数据丢失风险真实存在。修复方向：在 SettingsOverlay 导航分发处或 view 卸载前统一过 dirty 检查。

### D-15（已排除·2026-09-08 定性）可编辑 composer 输入文本后发送，批注附件静默丢失

- **定性结论（诊断实锤：假设 A）**：批注附件丢失系**回归脚本 sendMessage 双发结构误报**——disabled 分支先 force click 发一条（批注随它正常落库）→ append 推送清批注 store → 脚本接着 fill+Control+Enter 发第二条，第二条天然无批注。产品侧无 bug：修脚本单发化后，enabled 半段 fill+Control+Enter 单发，附件 DOM「消息附件 (1)」+ 查库 attachments_json 完整 annotate 附件双重铁证（seq=5）。原「fill 触发 onChange 清 store」假设证伪。
- 遗留：下划线投影验证（T-A2）当初因本条误报被掩蔽——附件已证落库，投影元素未命中（`MARKS r6o:0`）需另查（选择器与渲染态），随修复批次复验收口。
- 处置：Step 3（产品侧 runAgent 读取前移）不执行；Step 4 防御日志照做；e2e 工具修正（sendMessage 单发化）已落地。

- **现象（R7 补验两轮复现）**：划词→添加批注→chip 出现「批注:/批注验证.md」→输入文本发送→消息落库**无批注附件**（content_json 纯文本、kkv 无批注域）→重开文件无下划线投影（因批注根本没入库，投影功能未被证伪）。
- **对照实证（R3 第三轮）**：disabled composer（末条 user）+ chip 存在时 force 点发送（空文本）→ 消息「消息附件 (1)」含批注卡片 ✓。同链路仅差异：可编辑时 fill 了文本。
- **影响**：用户正常输入文字带批注发送是主路径——批注静默丢失，高风险数据丢失类。
- **排查方向**：executeRun 前 listChatAnnotateDrafts(sessionId) 返回空——草稿 store 在 fill/onChange 路径上被清或未被写入；对照 disabled 路径（不触 onChange）正常。重点查 chat-annotate-draft store 写入与 composer onChange 时序。**修正（2026-09-08 spec 诊断轮）**：fill/onChange 清 store 的原假设静态证据不支持（e2e 脚本 sendMessage 双发结构为最大嫌疑，见 spec 假设 A/B）；renderer 清 store 另有 rollback/rewind 路径（`rollback-annotate-restore.ts`，锚点为 assistant 时清全部草稿）；脚本修正与假设 B 修复均不成立时回本条重新定性。
- **附带**：批注下划线投影验证被本 bug 掩蔽，待修复后重验。
