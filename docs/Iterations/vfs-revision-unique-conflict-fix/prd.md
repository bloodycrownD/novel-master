# vfs_revision 唯一键冲突修复 PRD

## 背景

mobile 端用户实测：agent 调用 fs 工具执行 `rm`（以及部分 mv 伴生写场景）时报
`UNIQUE constraint failed: vfs_revision.entry_id, vfs_revision.version`，且一旦出现就对该文件持续复现，用户无法自救（只能绕开该文件）。

前期调研（见 `docs/apm/memory/20260827-vfs-revision-unique-conflict.md`）已定位根因不是 op-sqlite 驱动，而是版本链数据错位，共两条触发路径：

1. **head 回拨占号**：消息回滚 / 回合失败补偿会把文件的 head_version 拨回旧版本，但历史版本记录按设计永久保留（append-only，被 checkpoint 引用的版本不可回收）。此后系统在分配新版本号时用的是「当前 head + 1」，恰好撞上占号的历史版本，导致删除（墓碑）和写入必然失败。官方设计文档（`message-rollback-execution-redesign` 的 T-RB1）早已承认「head 落后于最大版本」是合法状态，现状实现没跟上这条拍板。
2. **发号器回退**（1.5.3 已部分修复）：文件编号发号器回退导致新文件复用旧编号，首个版本即撞车。官方启动自修复（entry-sequence-repair）本应兜底，但它内部吞掉了检测异常，检测失败会被当成「健康」静默放行——存量错位的库可能一直没被修好，且无任何日志可查。

## 目标（含成功指标）

- 用户在任何文件操作序列（写入 → 回滚 → 再写入/删除）之后，都能继续正常写入和删除，不再出现该唯一键报错。
- 一旦库中存在版本号错位（head 落后于历史最大版本），后续写入自动跳开占号段，无需用户干预、无需数据迁移。
- 启动自修复的检测失败不再静默：要么如实上报需要修复，要么带着日志失败，绝不伪装成「健康」。
- 成功指标：修复后 `packages/core` 的 VFS 与消息回滚测试全绿；新增的「回拨后写入/删除」回归用例通过；真实错位库（1.5.3 取证的那类数据形态）在模拟环境下首次写入即自愈。

## 用户与场景

- **写作用户（mobile/desktop）**：与 agent 长对话中反复修改章节文件，偶发使用消息回滚修正方向，之后继续让 agent 写/删文件——这是撞号的高频场景。
- **导入/恢复旧备份的用户**：库可能带着历史错位数据，升级到本版本后首次写文件即应自愈。
- **排查问题的开发者**：需要从日志里看到自修复是否运行、是否失败，而不是石沉大海。

## 范围

### 包含范围

- 新版本号分配策略调整：全部写入路径（更新、删除墓碑、递归删除、目录拷贝落盘）统一不再依赖「head + 1」。
- 启动自修复（entry-sequence-repair）静默失效漏洞修复：检测异常不再被吞成「健康」。
- bootstrap 对自修复结果报告的消费：失败要有日志。
- 上述行为的回归测试。

### 不包含范围

- op-sqlite / better-sqlite3 驱动层的事务实现改动。
- 存量库的数据迁移工具（按 append-only 语义，错位库无需迁移，新写入自动绕开）。
- 历史版本回收策略（sweep / checkpoint 引用计数）的调整。
- `vfs_revision` 表结构与触发器改动。

## 核心需求（3-7 条）

1. **R1 版本号分配防撞**：任何产生新版本记录的操作（文件更新、单文件删除、递归删除、拷贝写入），分配的版本号必须避开该文件的全部历史版本（含被 checkpoint 钉住的占号版本）。
2. **R2 乐观锁语义保留**：并发写入冲突（版本不一致）仍按现状报 CONFLICT，行为不回退。
3. **R3 引用计数配对不变**：版本引用的增减配对关系与现状完全一致，回滚与垃圾回收不受影响。
4. **R4 自修复不再静默失效**：自修复检测阶段出错时，不得判定为「健康」；应交由上层按「需要修复」保守处理，失败可观测（有日志）。
5. **R5 存量错位库自愈**：已处于「下次写入必撞」状态的库，升级后第一次写入/删除即成功，无需人工干预。
6. **R6 健康库行为不变**：正常库上版本号推进结果与现状等价，相关既有测试不改断言即通过（用例名如与语义有出入可调整措辞，断言值不变）。

## 验收标准

- **AC1（R1/R5）**：Given 文件写到 v5 且高版本被 checkpoint 引用，When 消息回滚把 head 拨回 v3，Then 对该文件执行 write 成功且新版本号为 v6，执行 rm 成功且墓碑版本不与任何历史版本冲突。
- **AC2（R1）**：Given 目录下多文件、其中部分文件 head 已回拨，When 递归删除该目录，Then 全部墓碑写入成功、无唯一键冲突。
- **AC3（R2）**：Given 文件 head 为 v3，When 携带 expectedVersion=2 的写入请求，Then 仍返回 CONFLICT 错误。
- **AC4（R4）**：Given 自修复检测查询抛错，When 启动自修复运行，Then 检测异常上抛（或被上层判定为需要修复），绝不返回「健康」；bootstrap 侧对失败报告有日志输出。
- **AC5（R3/R6）**：Given 健康库，When 跑 VFS 与消息回滚既有测试套件，Then 全部通过，引用计数闭合断言不变。
- **AC6（R1）**：Given 模拟 1.5.3 取证的错位库形态（发号器低于历史最大编号），When 修复后写入新文件并删除，Then 操作成功。

## 风险与待确认项

- 用户那次 **mv 报错**的具体上下文（app 版本、前后操作序列）未取到——按当前代码 mv 不写版本记录，推断报错来自旧版实现或同批次其它写操作；本 PRD 的修复对两种情况都有效，但「mv 场景」无法直接构造验收用例。
- op-sqlite 真机上读 `sqlite_sequence` 是否真的会抛错（即自修复静默失效的实际触发条件）**未经实锤取证**，R4 的修法不依赖该前提（不吞错总是对的），但根因描述里只能标注为推断。
- `resolveMaxRevision` 的 MAX+1 分支疑似不可达（死代码），是否顺带清理待实现阶段确认意图后决定，不影响本 PRD 验收。
