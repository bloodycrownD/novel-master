# 存储缓存去重与数据清理 PRD

## 背景

用户实测备份库 523MB，其中 `session_kkv_entry` 表的 `file_cache` 域（提示词文件缓存）占约 415MB：299 个唯一缓存内容被复制成 21198 行——因为缓存按会话隔离存储，每个会话（含 task 派生的子会话）首轮组装提示词时都会对工作区同一批文件各抄一份正文。以"商人与女奴"项目为例，320 个会话把同一批文件头缓存各存一份，平均每个内容重复约 71 次；去重后单份内容合计仅约 4MB。

同时，删除项目/会话虽已正确级联清掉逻辑行（探索已核实无孤儿数据），但 SQLite 删除只把页挂入空闲页链表，库文件物理大小不变；全仓没有任何空间回收能力（无 VACUUM、无 auto_vacuum）。用户没有任何手段让库文件瘦下来。

探索确认的关键约束（决定本需求形态）：

- 缓存"命中不校验 mtime、回合内前缀冻结"是有意设计（配合服务商前缀缓存命中），mtime 校验在历史迭代已拍板"另立项不做"；
- 置位/压缩/导入后清空缓存的真实目的是重置"可见历史首次引用"状态，清理必须保持会话粒度；
- 子会话缓存隔离（`kkvScopeSessionId` 恒等自身）是已拍板口径；
- 文件原文层（VFS 正文）已有全库内容去重先例（`vfs_content_blob` 按哈希共享 + 引用计数 GC），本需求是把这个模式带到提示词缓存层；
- 双端均无库体积展示 UI；mobile 执行通道现成，desktop 需新增 IPC；Agent 运行守卫先例现成。

## 目标（含成功指标）

治理提示词缓存的存储膨胀，并给用户提供数据库空间回收的手动能力，且**不改变任何提示词拼装与缓存清理的既有语义**。

成功指标：

1. 缓存去重迁移完成后，同规模库的缓存存储体积从"内容数 × 会话数"降为"内容数 × 1"（参照用户实测库：约 415MB → 约 4MB，含引用行开销）；
2. 数据清理完成后，库文件物理体积与逻辑数据量一致（空闲页接近 0），用户可感知"清理前后"体积对比；
3. 既有语义零回归：置位、压缩、导入缓存对齐、回滚截尾、子会话隔离、短提示首次引用判定的全部既有测试保持通过；
4. 双端（mobile / desktop）均可完成"查看库体积 → 执行数据清理 → 看到体积下降"的完整闭环。

## 用户与场景

- **重度多会话用户**：在少数几个项目里开过大量会话（含 agent 自动派生的子会话），工作区引用大批长文件（原著章节、设定集、大纲）。库体积随会话数近似线性膨胀，即使删掉旧会话/旧项目文件也不缩小。
- **典型场景一（存储治理后）**：用户升级应用，迁移自动清空存量缓存并落入新结构（逻辑缓存归零、重填即去重）；物理库体积经「数据清理」功能手动回收；
- **典型场景二（手动清理）**：用户删除了一批旧项目/旧会话后，进入存储配置（mobile「存储配置」页 / desktop 设置「备份与恢复」页），看到当前库体积与可回收提示，点击"数据清理"，等待完成，看到体积下降的反馈；
- **场景三（误导入超大文件后）**：超大文件本就不进缓存（既有降级闸门），用户通过数据清理与缓存冗余清理回收其他残留。

## 范围

### 包含范围

1. **缓存存储层去重（feature A）**：同一缓存内容全库只存一份，会话侧仅保留轻量引用；缓存内容的写入、命中、清理对会话侧的语义与现状完全一致；无引用的缓存内容可被回收（参照 VFS 正文的引用计数 GC 模式）；存量重复数据通过迁移一次性去重。
2. **数据清理按钮（feature B，双端）**：
   - 库体积展示（当前库文件大小，清理前后对比）；
   - 缓存冗余清理（回收无会话引用的缓存内容）；
   - VACUUM 空间回收（事务外执行，使库文件物理缩小）；
   - Agent 运行中禁用、执行中置灰/进度反馈、完成结果反馈；
   - 与云同步、备份导入导出的并发互斥。

### 不包含范围

- 缓存命中语义变更：不做跨会话命中复用、不做 mtime/版本校验（维持"命中无条件返回、回合内冻结"的既有拍板）；
- 置位/压缩/导入缓存对齐的清理粒度与时机变更（仍为会话级三件套）；
- 子会话缓存隔离口径变更（`kkvScopeSessionId` 恒等自身不变）；
- 自动触发清理（删除大量数据后自动 VACUUM 或弹引导）——仅提供手动入口；
- journal 模式切换（维持默认 DELETE 模式，不引入 WAL）；
- VFS 正文层（`vfs_content_blob`）的去重与 GC——已由历史迭代实现，本需求仅复用其模式。

## 核心需求（3-7 条）

1. **缓存内容全局单份存储**：同一缓存内容（含同路径不同展示档位各自的内容）在全库只落一份；会话的缓存域行为（写入、命中、按域清空）对外表现与现状一致，任何既有调用方无需感知存储方式变化。
2. **无引用内容可回收**：当内容不再被任何会话引用（如会话删除、置位/压缩清域、文件改名/删除后的残留键）后，对应内容可被垃圾回收；回收入口收敛为单一机制，禁止局部引用集误删（对齐 VFS blob GC 的既有纪律）。
3. **存量数据一次性迁移去重**：升级时自动清空现有按会话复制的缓存行（单步事务内完成，不搬运数据）；各会话下次组装提示词时按新结构重填，重填即天然去重。缓存为可再生数据，清空无信息损失；中断时事务原子回滚，再次启动幂等重跑。
4. **数据清理入口（双端）**：mobile 存储配置页与 desktop 设置「备份与恢复」页提供"数据清理"操作，执行"缓存冗余清理 + VACUUM"并展示库体积前后对比；Agent 运行中/其他数据库操作进行中时禁用。
5. **执行安全与反馈**：清理在数据库空闲时执行，执行期间阻止并发数据库操作（云同步、备份导入导出）；大库执行需有可见的进行中状态与完成结果（成功/失败原因）反馈；失败不影响数据完整性。互斥口径分端说明：desktop 实现双向互斥（Agent/云同步/清理互相禁用）；mobile 的「禁用」为既有交互口径——按钮守卫 + 文案提示（Agent 运行中/处理中…），与云同步的跨页互斥不在本迭代范围（与既有备份导入导出行为一致）。
6. **体积可感知**：双端可查看当前数据库文件体积；清理完成后展示前后对比，让用户确认回收效果。

## 验收标准

**Feature A（缓存去重）**

- AC-A1（迁移去重）：Given 一个含多会话重复缓存的真实库（如用户备份库 523MB），When 升级迁移完成后，Then 存量缓存行清空（缓存存储为 0），且其他域数据不受影响；会话重新组装后缓存按新结构重填，重填后同规模内容收敛为单份存储（约 4MB 量级），各会话缓存域行为语义与迁移前一致；
- AC-A2（语义零回归）：Given 既有测试套件（置位、压缩、导入缓存对齐、回滚截尾、子会话隔离、短提示/首次引用、缓存读写单测），When 全量运行，Then 全部通过，无断言修改；
- AC-A3（新会话不再膨胀）：Given 迁移后的库，When 新建会话并触发与历史会话相同的工作区文件引用，Then 库中缓存内容不新增重复份数（仅新增轻量引用）；
- AC-A4（会话删除回收）：Given 会话 A 与 B 引用同一缓存内容，When 删除会话 A，Then 会话 B 仍正常命中该内容；当 B 也删除后，该内容可被冗余清理回收；
- AC-A5（迁移可重入）：Given 迁移中途被中断（如进程被杀）的库，When 再次启动，Then 迁移事务原子回滚后幂等重跑并最终完成，无数据损坏、无残留中间态。

**Feature B（数据清理按钮）**

- AC-B1（体积展示）：Given 双端存储配置页，When 进入页面，Then 可见当前数据库文件体积；
- AC-B2（清理生效）：Given 一个删除过大量数据、空闲页可观的库，When 点击"数据清理"并完成，Then 库文件体积明显下降（空闲页接近 0），页面展示前后对比；
- AC-B3（守卫生效）：Given Agent 正在运行（或有数据库操作进行中），Then 清理按钮禁用；清理执行期间：desktop 导入导出/云同步双向不可发起；mobile 导入导出同页互斥成立，云同步跨页互斥不在本迭代范围（沿用既有口径，与既有备份导入导出行为一致）；mobile 侧「禁用」判定为「点击无效 + value 文案提示」；
- AC-B4（失败安全）：Given 清理因磁盘空间不足等原因失败，Then 数据库保持可用、数据无损坏，用户收到失败原因提示；
- AC-B5（双端一致）：上述行为在 mobile 与 desktop 一致成立。

## 约束与依赖

- 遵循仓库 schema 纪律：新表走 canonical DDL + 版本登记三件套；数据迁移遵守"不得提前登记空占位""大库分批、事务外、可跨 boot 重入"的既有约定（本需求的存量缓存迁移为单步清空事务、无数据搬运，不适用分批/事务外条款）；
- VACUUM 不能在事务内执行（bootstrap/迁移事务内不可为），须启动后手动触发；
- desktop 侧需新增一条 IPC 通道（renderer 与数据库隔离的红线不可绕过）；
- mobile 侧 VACUUM 走 op-sqlite 异步执行（原生线程），desktop 为同步阻塞（需 UI 状态遮盖）。

## 风险与待确认项

- **大库迁移耗时**：已拍板（SPEC 阶段确认）——存量迁移采用清空重填口径（单步事务清空 file_cache 域，不搬运数据，见核心需求 3），原"21198 行 / 415MB 搬运耗时"风险不再成立；
- **缓存冗余清理的判定口径**：文件已删/改名后的残留旧键（现状明确不清）在去重后是否顺带纳入冗余判定，SPEC 阶段定；
- **desktop 主进程阻塞时长**：better-sqlite3 同步 VACUUM 大库会阻塞主进程数秒到数十秒，UI 遮罩文案需管理预期。
