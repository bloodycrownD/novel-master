# 上下文占用计数大修（context-usage-overhaul）PRD

## 背景

双端聊天的「上下文占用」chip（desktop 会话详情抽屉 / mobile ChatMetaBar）当前链路：上次 completed run 的 API `prompt_tokens` 优先（session KKV 持久化），值不可用时本地计数——把全部可见消息 + workplace 前缀序列化成整段文本，按模型家族选词表一次性全量 encode。2026-09-28 两轮探索（见 `docs/apm/memory/20260928-context-usage-token-perf.md`）实锤三类问题：

1. **性能**：本地计数无任何消息级缓存——每 step 落库、run 结束、回滚、压缩/置位都把整个上下文重算一遍且无防抖；精确档（desktop WASM）与 mobile GPT 路径的全量 encode 未走分块保护，长无标点中文串命中 O(len²) 病态档（实测 12K 字符 88~93 秒）；desktop 在主进程同步执行阻塞 IPC。压缩/置位只改变「可见消息集合」，消息内容与 token 数并没变，却被整轮重算。
2. **标签可读性**：「预估 / 上次请求」只表达值的来源（本地估算 vs 上次 API 真值），不展示用了哪张词表；`~` 前缀表达近似不直观。GLM 用户看到「预估」误以为家族路由有 bug（实际 glm.json 正在生效）——观测缺口真实造成了误解。
3. **兜底口径分裂**：JS 侧兜底已升级为 cl100k 分块计数（v1.5.23），但 Android Kotlin 原生桥失败兜底仍是字符折算 `ceil(len/3.35)`（中文低估 82~84%）；且 node 驱动与 Kotlin 两处在词表加载失败时 counterKind 仍谎报家族名，观测失真。

用户拍板（2026-09-28）：本迭代做「大修」——消息级缓存 + 标签体系更换 + 兜底统一；兜底统一走 gpt 分词器（cl100k）口径，理由是反正都是估算、cl100k 通用性远好于字符除法。

## 目标（含成功指标）

1. **消灭全量重算**：消息内容不变则 token 数直接复用；缓存全命中路径零 encode；压缩/置位/回滚后刷新只补算新增边界。成功指标：同会话无变更连续两次刷新，第二次不发生任何 tokenizer encode；含 12K 无空白中文串的单条消息计数 ≤1s（分块保护生效）。
2. **标签自解释**：源记号直接展示实际使用的词表（或「远程」），连接符区分精确/估算，双端口径一致，用户不再需要猜测数值来自哪张词表。成功指标：典型组合（远程 / 家族词表精确 / OpenAI 家族精确 / gpt 兜底近似）标签正确呈现，`~` 前缀退役。
3. **兜底统一**：Android 原生失败不再字符折算，全部端与档位的兜底数值同口径（cl100k）；counterKind 如实上报。
4. **实现收敛**：编码表（BPE ranks / 词表资产）的构造与缓存收敛为单一实现路径，消除三份独立缓存与同进程重复建表（cr-fix-spec-v3 OQ#2 一并了结）。成功指标：同进程同一编码至多构造一次，既有预热行为保留。
5. **指标详情可视**：双端流式指标条可点击，弹出详情面板展示最近请求与会话累计的 token 计量。成功指标：弹窗内可读到输入/输出/缓存命中率/工具调用数/消息数，口径与用量统计页一致。

## 用户与场景

- 双端普通用户在聊天界面查看「上下文占用」，据此判断何时该压缩/置位。
- 长会话、消息含大段中文正文（小说创作场景常态）的用户：当前会遇到 chip 迟迟不刷新甚至界面卡顿。
- 排查「模型到底用没用对词表」的开发者/高级用户：当前无法从 UI 区分词表来源。

## 范围

### 包含范围

1. **消息级 token 缓存**：以「序列化后的消息块（含角色包装）→ token 数」为缓存粒度，消息内容不变则命中；新增/编辑/删除单条只失效对应条目；压缩/置位/回滚只改变可见集合、命中条目直接复用。workplace 前缀、system、tools 段同样纳入缓存。缓存键须感知词表/编码差异（换模型自动 miss）。
2. **全路径分块保护**：所有本地计数路径（desktop 精确档 WASM、mobile GPT 家族、各兜底档）统一走 ≤64 字符分块增量计数，消灭病态档。
3. **刷新防抖合并**：chip 刷新事件合并，run 内多 step 不再逐 step 全量重算。
4. **标签体系更换**：完整标签 =【源记号 连接符 百分比 上下文 token 数】。源记号 = 实际使用的词表——`gpt`（cl100k/o200k：OpenAI 家族精确计数与一切 cl100k 兜底）或家族名（`glm` / `claude` / `deepseek` / `gemma` 等，该家族词表精确计数）或 `远程`（上次请求 usage 真值）；连接符：`=` 精确、`≈` 估算。典型形态：`远程 = 42% 55/128K`（usage 真值）、`glm = 42% 55/128K`（glm 词表本地精确）、`gpt = 42% 55/128K`（OpenAI 家族本地精确）、`gpt ≈ 42% 55/128K`（cl100k 本地估算兜底）。源记号如实反映实际词表——家族词表加载失败退 cl100k 时显示 `gpt ≈` 而非原家族名（标签体系天然杜绝谎报）。双端一致，`~` 前缀取消。字符折算仅在词表彻底加载失败的异常终极档出现，不占正常档位，其记号由 spec 拍板。
5. **兜底对齐与诚实标注**：Android 原生桥失败路径对齐 cl100k 口径（不再字符折算）；node 驱动与 Kotlin 的 counterKind 谎报修复（兜底如实报 heuristic 档）。
6. **编码表缓存收敛**：node 驱动 / RN 驱动 / mobile shim 三处独立的编码表缓存收敛为统一单例路径，同进程不重复建表；失败缓存不重试（OQ#6）等既有语义是否顺带调整由 spec 拍板，但收敛本身是本迭代验收项。
7. **指标详情弹窗**：双端流式指标条（mobile 指标条、desktop 指标条）支持点击弹出详情，形态按平台惯例（mobile 底部 sheet / desktop popover 或面板，spec 定）。内容两段式——**最近请求**（模型名、输入/输出 token、缓存命中拆分与命中率）+ **会话累计**（消息数、工具调用数、累计输入/输出、当前上下文占用）。口径与用量统计页（token-usage-stats）一致（anthropic 计费口径加回 cache 列）。

### 不包含范围

- 实时输出速率链路（stream metrics，v1.5.23 已落）不动。
- 「usage 基线 + trailing 偏移」口径变更（pi 调研 A 项）不引入——本迭代缓存是本地计数中间层的优化，显示语义保持「API 优先、miss 走本地（缓存加和）」。
- 压缩判定阈值、counterKind→0.85 安全系数的联动语义不动。
- 不更换分词器实现库（js-tiktoken/tiktoken/@agnai 保持现状；gpt-tokenizer 等替换另议）。
- 用量统计页（token-usage-stats）不动。

## 核心需求

1. **缓存语义**：本地计数结果按消息块缓存；同内容同词表必同值；消息生命周期事件（编辑/删除/回滚恢复）精准失效；压缩/置位不失效条目本身（只改变可见集合）；进程内缓存为底线，是否持久化由 spec 决定。
2. **计数正确性**：全路径分块后计数误差 ≤1%（对齐既有护栏）；「精准」档与该家族词表全量计数结果一致性维持现状口径；缓存命中路径与逐条现算结果一致。
3. **标签判定**：源记号由实际生效的计数路径推导（tokenSource=api → `远程`；counterKind=家族名 → 该家族名；cl100k/tiktoken/heuristic 兜底 → `gpt`），连接符由计数精度决定（精确 → `=`，近似 → `≈`）；映射关系双端单源维护。
4. **双端一致**：同一模型同一会话在 desktop 与 mobile 上源标签一致（含 GPT 家族当前双端 counterKind 粒度不一致的既有问题，须在本迭代内对齐）。
5. **兜底诚实**：任何未用上「该家族词表精确计数」的路径，counterKind 不得报家族名；Android 失败兜底数值口径与 JS 侧一致。
6. **缓存路径单源**：编码表的构造与缓存单一实现路径，双端各进程内同一编码至多一份实例；流式估算与上下文占用计数共享同一份；预热行为保留。
7. **指标详情口径**：弹窗数据与库内逐消息 token 列（prompt/completion/cache_read/cache_creation）同源；「最近请求」取本会话最近一条有 usage 的 assistant 消息；「会话累计」只统计本会话；缓存命中率沿用统计页计费口径；无 usage 数据的字段显示占位而非错误值。

## 验收标准

- **缓存命中**：Given 会话状态未变更，When 连续两次触发 chip 刷新，Then 第二次不发生任何 tokenizer encode 且数值与首次一致。
- **压缩/置位免重算**：Given 会话已有缓存，When 执行压缩或置位后刷新，Then 仅新增可见边界增量计数，已缓存消息块零重算，数值与全量重算一致（误差 ≤1%）。
- **病态输入护栏**：Given 单条消息含 12K 无空白中文字符串，When 本地计数，Then 耗时 ≤1s。
- **标签形态**：Given API 真值命中 → 显示「远程 = N% X/Y」；Given glm 模型家族词表计数 → 显示「glm = N% X/Y」；Given OpenAI 家族精确计数 → 显示「gpt = N% X/Y」；Given 家族词表不可用退 cl100k → 显示「gpt ≈ N% X/Y」。双端各档一致，无 `~` 前缀残留。
- **兜底对齐**：Given Android 原生桥加载失败，Then 计数结果与 JS 侧 cl100k 兜底口径一致（非字符折算值），counterKind 如实报 heuristic 档。
- **编码表单例**：Given 同一进程内两条计数路径（流式估算与上下文占用计数）使用相同编码且已完成预热，Then 该编码只构造一次（构造计数 =1），第二次路径直接命中缓存。
- **指标详情弹窗**：Given 会话已有带 usage 的 assistant 消息，When 点击流式指标条，Then 弹窗展示最近请求（模型/输入/输出/缓存命中率）与会话累计（消息数/工具调用数/累计 token/上下文占用），数值与用量统计页同源同口径；无 usage 数据时对应字段为占位显示。
- **回归**：既有增量计数器护栏测试（误差、性能门限）全部不回退；压缩判定行为（counterKind→安全系数联动）不变。

## 约束与依赖

- 服从既有拍板：「实时 token 指标语义（2026-09-26）」「上下文占用口径治本（caliber-unify）」——API 值优先、append 失效、Token 单引擎读口不动。
- 移动端 Hermes 无 WebAssembly（真机实测），纯 JS 约束不变。
- Kotlin 侧改动需出包真机验证；改 core dist 消费的包须重建 dist。
- 计划分四个 feature 子目录推进：message-token-cache / token-source-label / fallback-caliber-align / metric-detail-sheet（spec 阶段可调整）。

## 风险与待确认项

- 消息级缓存与「append 即失效 API 值」两套失效规则的边界须在 spec 中写清（缓存条目是本地计数中间产物，不受 API 值失效影响，但显示层语义不变）。
- 序列化若存在跨消息格式依赖（消息块非逐条独立），缓存粒度需 spec 核实调整。
- 缓存内存占用上限与淘汰策略（超长会话）待 spec 定。
- 编码表缓存收敛涉及 node/rn 驱动与 mobile shim 三处装配线，回归面须覆盖双端启动、流式估算与上下文占用双链路；失败缓存不重试（OQ#6）是否顺带修复由 spec 拍板。
- desktop 是否顺带把计数挪离主进程（worker 隔离）——防抖+缓存落地后主进程负担已大降，列为可选增强，不作为本迭代验收项。
- 指标详情弹窗与 desktop 会话详情抽屉存在信息重叠（两者都可能展示 token 信息），重叠内容的归属与交互层级由 spec/设计拍板。
