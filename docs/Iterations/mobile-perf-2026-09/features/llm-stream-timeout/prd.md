# LLM 流式黑洞挂死根治 PRD（feature ⑤ 回炉）

> **终版语义修订（2026-09-26，产品拍板）**：本文以下为回炉版初稿语义。实施后按产品拍板修正两处：① **流式不设任何固定空闲界**——初稿的「流中 30s idle 安全网」（watchdog）被真机实锤误杀（GLM 工具调用默认服务端憋生成、期间零数据），已整体退役（原语与导出保留、无接入方）；**死流由用户手动终止（点停止），唯一自动兜底是整调用预算**——首字黑洞自动上限 = 单次 10 分钟 × 重试次数（最多 3 次尝试）≈ 30 分钟。② **`Connection: close` 是条件化的**——走原生传输层时不设（连接池复用恢复），原有 XHR 通路保留。逐条见 spec「终版语义修订」节与 ⑦ `docs/Iterations/llm-stream-native/spec.md` §2 实施修正记录。

## 背景（回炉依据，2026-09-24 实证更新）

用户原始 bug：**任何一个高速模型，在高速输出完成之后，想要再次请求时进入长时间等待**；重启应用或更换模型后恢复正常。应用本身不死，该请求「生成中 · 0 字 · 计时不动」永远不收敛。

初版方案（watchdog 首字 120s / 空闲 90s）被用户否决：治标不治本、阈值与用户「十几秒手动重试」的节奏脱节、first-chunk 固定阈值会误杀缓冲型（非流式）正常模型。**回炉重新归因，证据链已闭合**：

1. **黑洞本体（模拟器 r3 实测复现）**：RN 0.85.3 Android 的 OkHttp 栈 connect/read/write/call 四个超时**全为 0（无限）**（`OkHttpClientProvider.kt` L49-54）；连接池默认 5 条 / 5 分钟。上一次高速流结束后的连接回池，若对端已静默死亡（半开），池内健康检查**防不住**（空闲 <10s 连探测都不做；>10s 的 1ms 探测对无 FIN 的半开连接误判健康）。复用死连接 → 请求写进本机 TCP 缓冲即「成功」→ 读永久阻塞 → 四个 XHR 回调一个不来 → run 的 await 永挂。「换模型恢复」=换 host 池内无候选新建连接；「重启恢复」=进程内连接池清空——与用户两条恢复路径精确吻合。模拟器实测：杀服务器后请求黑洞、点停止反而触发自动重试再进黑洞、服务器复活也不自愈。
2. **误重试（实测发现的新病灶）**：挂死态点停止，abort 错误被重试层判为可重试，自动重发又进同一个黑洞——用户的「手动重试」被劫持成无限僵尸。
3. **计时冻结（实测）**：挂死时指标条秒数停摆（「生成中 · 3.4s」永远不变）——elapsed 渲染是事件驱动的，无流事件即无重渲染。用户「跑了十几秒」的感知信号失真。
4. **流式增量停摆（并存病灶，非本 bug 主因）**：真机流式「前 37s 渐进 → 中途停摆 → 尾部一次性倾泻」；根因为 RN XHR 管线每事件超线性成本（`_response += chunk` O(n²) 累积 + GC 风暴 + 网络事件与定时器同队列积压）。数据最终完整、onload 最终交付——**不产生挂死**，仅 UX 劣化。本期不修，登记为 Phase 2（原生 SSE 模块）方向。

## 目标

高速流之后的下一次请求**不再落入死连接黑洞**；万落入（h2 等残余场景）也能有限时间收敛；用户手动停止**干净收尾**（不僵尸重试、会话立即可再发、新请求走新连接）；挂死期间计时真实走动。

## 核心需求

1. **消灭复用入口**：mobile XHR 流式请求不再把连接留在池里（`Connection: close`；**终版：条件化**——原生传输层分支不设并恢复池化，原生未注册/加载失败回落 XHR 时保留该头）；
2. **整调用兜底**：XHR 请求设 `xhr.timeout`（映射 OkHttp callTimeout，RN 0.85.3 已实现）——connect/写/读全周期、h1/h2 通吃的确定性兜底；触发时按「是否已收到数据」分级收敛；
3. ~~**流空闲安全网**：流中静默超阈值 → 以超时错误收敛（不自动重试、落既有失败链）；**不做首字超时**（缓冲型模型零误杀）~~ **【终版：整体退役】**——流式不设任何固定空闲界（合法停顿与死流无法区分，固定阈值必然误杀）；**不做首字超时**的结论保留并推广到流中；死流由用户手动终止、自动兜底仅整调用预算；
4. **abort 语义修正**：用户停止绝不触发自动重试，run 干净收尾（partial/失败占位按既有链）、registry 反注册、会话解锁；
5. **计时活钟**：run 进行中秒数真实走动（事件断流也走）；
6. **观测**：超时/挂死收敛时打点（是否收到过数据、已收字节数、缓冲量）。

## 验收标准

- AC-1：模拟器复现路径（大流完成后杀服务器 → 下一次请求）：停止后 run 干净收敛、无自动重试痕迹、会话可立即再发；服务器恢复后再发**成功**（新连接）；
- AC-2：正常长流（慢速模型、thinking 长静默段、工具调用服务端憋生成段）零误杀；缓冲型慢启动模型（首字 >60s）不被任何机制自动杀死。**终版口径**：流式**无固定空闲界**（watchdog 已退役），任何合法停顿都如实等待——「零误杀」由「不存在空闲阈值」保证；**死流由用户手动终止**（点停止即时收敛），不做自动空闲检测；
- AC-3：`xhr.timeout` 触发路径收敛为可分类错误（无输出→可重试语义；有输出→失败链），不冒充用户取消、不被吞成 partial；
- AC-4：core 全量 + 双端定向测试全绿；模拟器 e2e 黑洞场景走查通过。

## 已知限制（登记）

- **终版：流式无固定空闲界**——合法停顿（思考、工具调用服务端憋生成、排队）与死流不可区分，故不设任何自动空闲检测；**死流由用户手动终止**（点停止走 sseAbort 链，干净收尾），完全不操作时的自动兜底是整调用预算（单次 10 分钟 × 最多 3 次尝试 ≈ 30 分钟）。若需更快的自动收敛，属后续迭代议题（收窄预算或引入可区分的活性信号）。
- ~~watchdog 依赖 setTimeout：app 后台 timer 停摆期间同停（与 ③ 同根因），后台挂死检测回前台后生效；不为本期目标。~~（watchdog 已退役，该限制随本体消解。）
- `Connection: close` 在 HTTP/2 下被协议剥离（无效但无害）——h2 黑洞由 `xhr.timeout` 兜底覆盖（终版：仅回落 XHR 路径设该头）。
- 仅覆盖流式请求（postSse 路径）；非流式请求挂死为既有行为，不在本期目标内（⑦ llm-stream-native 已收编非流式通路，归其验收）。
- 流式增量停摆（渐进渲染中断）为 Phase 2 议题（原生 SSE 模块），本期不修（⑦ llm-stream-native 承接）。
