## 一、执行协议（所有子代理必须遵守，主代理派单时逐份写入 prompt）

1. **报告落盘、信封一行**：代理的全部产出写进本迭代 `raw/` 下自己的报告文件；
   返回给主代理的消息**只有一行**：
   `done | <报告绝对路径> | findings: P0×n P1×n P2×n P3×n | top: <≤30字最重要发现>`
   禁止在返回消息里复述报告内容——主代理上下文是全编队最稀缺资源。
2. **报告 schema（markdown，固定结构）**：
   - front matter：`zone` / `agent`（机位类型）/ `files_scanned`
   - `## 摘要`（≤150 字：这个区域是干什么的）
   - `## 职责与边界`
   - `## 对外接口`（导出的关键符号/类型）
   - `## 数据访问`（触碰的表 / KKV 域 / 文件路径，带 file:line 证据）
   - `## 依赖关系`（import 了谁；被谁消费）
   - `## 发现清单`（每条：`F-<zone>-<n> | P0~P3 | file:line | 引文≤3行 | 描述 | 建议 | 置信 confirmed/suspected/intentional`）
   - `## 争议与存疑`（拿不准的明说，不许抹平分歧）
3. **决策感知**：开工先读 `docs/apm/RULE.md` 相关节目。看起来冗余但 RULE/迭代文档写明是
   故意设计的（迁移双形态、兼容分支、拍板接受的盲区等），标 `intentional` 并引用出处，不当问题报。
4. **证据要求**：每条发现必须带 file:line 与原文引文；数字结论必须实测（不许照抄别的文档）。
5. **只读纪律**：禁 git 写；禁创建/修改 `docs/apm/`；定位用 `grep -rln` 列文件名再定点读；
   大文件分段读；终端输出截断。
6. **对抗纪律**：对抗对（辩护者/检察官）与独立双扫的成员互不知道对方存在，禁止读取对方报告。
7. **派遣登记（主代理纪律，2026-10-01 用户拍板）**：每次派遣**先**在 `registry.md` 登记（wave/zone/agentId/状态/报告路径），收割时更新信封摘要——主代理上下文可能被压缩，编队状态必须全程落盘可重建。压缩后恢复流程：PLAN.md（本协议）→ status.md（裁决日志）→ registry.md（编队状态）→ 主仓 docs/apm/memory/20260930-mega-cr-feasibility.md（决策史）。

## 四、S 阶段：fix-spec 化与 spec-check-loop（2026-10-01 启动，用户指令）

> 背景：ledger-v2 是「问题台账 + 波次提案」，不是 execute-ready spec（用户 2026-10-01 认定）。

### S 阶段协议（在第一章七条之上追加）

8. **spec 分片 schema**：每条目必须含七要素——病症 / 证据（file:line+引文，**撰写时须重新打开
   `fe79b781` 代码核对，禁止照抄台账行号**）/ 修法（文件·函数级步骤）/ 验收（可测断言或命令+期望）/
   测试策略（新增或改动的测试文件+用例名）/ 回归线（必须保持绿的既有测试）/ 依赖（前置条目与拍板项）。
   分片落点：`fix-spec/wave-*.md`；总纲：`fix-spec/SPEC.md`；编排状态：`fix-spec/state.md`。
9. **审查轮形态（spec-check-loop 适配，v2 编排升级 2026-10-01 用户问询后）**：
   **流水化**——分片撰写完成一个，立即放量该片的 reviewer，不等全齐（层间依赖是「本片 spec 齐活」，
   只有 judge 需要等全部 reviewer）。reviewer 粒度 = **条目组**（每 3~5 条一个 readonly 机位，
   逐条对照代码验证七要素：行号在位？修法可行？验收可测？依赖闭合？），外加每片一个债务池抽验机位
   （本簇 P2/P3 ≥10%）。**全局 judge 仍为 1 个**（读全部 reviewer 报告 + spec 全文 + 关键代码抽查，
   裁跨片矛盾/依赖图/覆盖完备性，给 Go/No-Go——全局视野不可拆分）。
   judge 禁止仅凭 reviewer 报告下结论。reviewer 报告落盘 `raw/sr<N>-<片>-<组>.md`，返回信封一行。
   **粒度纪律**：不在撰写/审查层做「一条一个机位」——同文件多条目（agent-runner.ts、
   sqlite-message.repository.ts 等）与 PR 打包语义（云同步同 PR、P1-S 批次）要求修法在同一边界内
   协调，条目级拆分会产出互相冲突的修法，judge/doc-fix 缝合成本反而拉长轮次；平台并发槽也会把
   超额机位排队（W1-W11 实测墙钟不随并发数线性降）。单条深查仅在 reviewer 报可疑时临时加派。
10. **doc-fix**：not-ready 时由主代理直接编辑 fix-spec 分片闭合 must-fix（不派子代理改 spec）；
    同一 must-fix ≥3 轮不闭合 → blocked 请用户拍板。轮次上限 5。
11. **拍板项处理**：ledger §7 的 17 项不替用户拍。spec 主文按「默认建议案」撰写 + 备选差异注记 +
    `blocked-by-decision` 标记；终局时随 execute-ready 确认一并请用户拍。
12. **范围**：spec 化对象 = Wave A–E 执行面（全部 P0 + P1 + 入选 Wave 的 P2/死码/钩子）；
    其余 P2/P3 留台账作债务池，reviewer 每轮对本簇债务池做 ≥10% 抽验（定级合理、无重复、无已修）。
