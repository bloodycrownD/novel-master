# message-rollback-execution-redesign PRD

## 背景

Message Checkpoint v2 已定产品合同：Agent 消息完成后为会话工作区打**整树** `{路径 → revision version}` 检查点；用户回滚某条消息时，截断其后对话，并把工作区**正文**恢复到该检查点（或约定 prior）完成态。`vfs-revision-storage-optimize` 引入同文不升版、内容指纹共享与压缩存储，并明确**不改变**上述回滚对外语义。

在此之上已落地两轮战术优化（同 version / 同 content_hash 短路、checkpoint 指针 DISTINCT、批量预取 hash），真机长会话回滚从数秒降到约 **1s 内**。剩余体感主要来自：

- 回滚仍由应用层多轮编排数据库访问（计划 → 缺失检查 → 协调工作区 → 截断 → 打扫历史），移动端桥往返固定成本高；
- 打扫历史时仍可能**现算**「哪些版本还被引用」，并在热路径上做全库内容块回收扫描。

外部评审与内部对齐后的方向是：在**不改产品语义**的前提下，把回滚热路径改成「数据库侧闭环 + 写时维护可达性」，而不是继续堆局部 SQL 微优化。本迭代验收范围定为 **B 档**（见「范围」）。

## 目标（含成功指标）

| 目标 | 成功指标 |
|------|----------|
| 缩短用户可感知回滚等待 | 在「约百级文件、长会话多检查点」的真机场景下，完整回滚（含截断对话与工作区对齐）的核心耗时相对本迭代基线（约 0.9s 量级）再明显下降；热路径不再被「全库内容块扫描」主导 |
| 减少应用层编排往返 | 一次用户确认的回滚，应用层与数据库之间的**编排往返次数**从「多阶段多次往返」收敛为**极少次**（理想：一次事务脚本 + 至多一次取回「必须由应用层写盘」的少量路径） |
| 消灭回滚时现算可达集 | 回滚打扫版本历史时，**不必再**为建可达集而拉取并去重全会话检查点指针；改为依赖写路径维护的引用信息（或等价写时维护） |
| 语义不变 | 回滚后用户读到的工作区正文仍等于目标检查点完成态；live 版本号仍允许高于锚点版本（正文/指纹一致即可）；内容块回收不得误伤其它会话仍引用的正文 |

## 用户与场景

| 角色 | 场景 |
|------|------|
| 移动端写作者 | 长会话、工作区文件较多时，长按消息回滚；确认后希望尽快看到对话截断与文件恢复，而不是长时间无反馈卡顿 |
| 桌面端写作者 | 同上；回滚后资源管理器/预览应与工作区一致（现有体验 parity 保持） |
| 使用「撤销发送」的用户 | plain user 消息回滚（含锚点删除、工作区回到发送前）行为与现网一致，仅等待变短 |
| 遇到快照缺失/工作区恢复失败的用户 | 现有二次确认降级路径仍可用（本迭代不以此为主需求，但不得破坏） |

## 范围

### 包含范围

1. **回滚热路径 SQL 闭环（A 档）**  
   - 将计划、截断、可达清理中适合下沉的步骤收敛到**同一数据库事务脚本**（或极少次往返）；应用层主要传入锚点并处理「必须解压写盘」的少数路径。  
   - 截断对话与检查点改为数据库侧完成，避免为拼删除列表而先把整段消息拉进应用层。  
   - 删除不可达版本行采用反连接/集合差（不在应用层枚举会话全部历史版本键再逐条删）。  
   - 同 version / 同 content_hash 跳过写盘的行为保留或内化为数据库侧筛选「真正需要写」的路径列表。

2. **内容块回收移出回滚热路径**  
   - 用户回滚完成、工作区可用，**不要求**同一次操作内完成全库无引用内容块物理删除。  
   - 内容块回收改为空闲/后台/周期性任务，且仍遵守「全库引用安全、不得误删他会话仍引用的块」。  
   - **算法唯一入口**仍为 `collectAllReferencedHashes` + `ContentStore.gc`（经 `runDeferredBlobGc` 封装）；与 revision 打扫解耦，**触发可 deferred**，禁止旁路第三套 gc 实现。

3. **引用计数（或等价写时维护）（B 档增量）**  
   - 在版本历史行上维护「仍被多少检查点指针 / live 头引用」的计数（或等价结构）。  
   - 打检查点、写文件改 head、截断/删除检查点时更新计数；回滚打扫时按「计数归零（或约定阈值）即可删」执行，**不再**为每次回滚全量重算可达集。  
   - 计数策略须**保守**：宁可偏高多留几行历史，不可偏低导致误删仍被引用的版本；并提供可在空闲时运行的校验/纠偏手段。

4. **产品语义与既有入口保持**  
   - rewind / undo_send、降级「仅删对话」、revision 缺失回补等用户可见行为保持可用；本迭代以执行架构与性能为主，不重做交互文案（除非实现被迫微调且不改变含义）。

### 不包含范围

1. **检查点改为只记变更 / 存储层 delta 链**（可对外仍暴露整树）——留给后续迭代；本迭代检查点对外仍是整树指针语义，物理行可继续按现网整树写入（引用计数在整树重复指针上仍正确，只是写放大仍在）。  
2. **强制全面调整 SQLite PRAGMA 作为验收项**（可作为实现期按现网基线评估的加分项，不阻塞本 PRD 验收）。  
3. git 式正文 delta/pack；把检查点改存 blob id 替代 version。  
4. 重做 Mobile/Desktop 回滚确认文案、进度条 UX（可另立体验迭代；本迭代不强制）。  
5. 改变「Agent 运行中禁止回滚」「hidden 消息不可回滚」等门禁。  
6. 再叠一层与本架构无关的局部 SQL 微优化作为主交付（应纳入上述闭环/引用计数设计）。

## 核心需求（3-7 条）

1. **热路径闭环**：用户确认回滚后，核心数据变更应在数据库侧以事务方式完成截断与版本打扫的主体工作；应用层不得再依赖「多轮查询 → 内存建可达集 → 多轮删除」作为主路径。  
2. **按需写盘**：仅当目标正文与当前工作区不一致（含文件缺失需重建、或需删除多余文件）时，才对该路径执行解压/写入；已一致的路径不得再走重成本写路径。  
3. **写时维护引用**：版本行的可删除性由写路径维护的引用信息决定；回滚时删除「已无引用」的版本行，而不是每次拉取全会话检查点指针现算。  
4. **热路径不扫全库内容块**：回滚成功返回前，不得以「扫描全库 entry/revision 指纹再删 blob」作为同步必做步骤；内容块回收延期且安全。  
5. **语义合同**：回滚后工作区正文 = 目标检查点完成态；允许 live 版本号高于锚点版本；内容块回收不得删除仍被任一会话引用的块。  
6. **模式齐全**：rewind 与 undo_send（含发送前 prior / 空树）行为与现网一致；失败降级与缺失回补路径仍可完成用户已理解的选择。

## 验收标准

- [ ] **Given** 长会话（多检查点、约百级文件）、工作区多数文件正文已与目标检查点一致，**When** 用户完整回滚，**Then** 对话截断与工作区正文正确，且核心等待相对本迭代基线明显缩短；诊断上热路径不再出现「为建可达集而加载数千重复检查点指针」或「同步全库内容块扫描」占主导。  
- [ ] **Given** 目标检查点与当前工作区仅少数路径正文不同，**When** 回滚，**Then** 仅这些路径发生实质写盘/删除；其余路径不因「走过协调逻辑」而产生解压写盘。  
- [ ] **Given** 回滚截断删除了若干检查点，**When** 打扫版本历史，**Then** 仅删除引用已尽的版本行；仍被保留检查点或 live 头引用的版本行仍在，且之后仍可回滚到那些检查点得到正确正文。  
- [ ] **Given** 库内存在其它会话仍引用的共享内容块，**When** 本会话回滚并在之后触发内容块回收，**Then** 其它会话仍可正常读出其文件正文。  
- [ ] **Given** plain user「撤销发送」与 assistant「回退到此消息」，**When** 分别回滚，**Then** 消息范围与工作区对齐规则与现网一致（含 undo_send 的 prior/空树）。  
- [ ] **Given** 工作区恢复失败或快照缺失，**When** 用户选择现有降级/回补确认，**Then** 行为与现网产品口径一致（仅删对话或继续回补后回滚）。  
- [ ] **Given** 引用计数（或等价结构）在异常路径下可能偏高，**When** 运行 `repairRefCounts`（API 已实现，T-RB-REF-CONSERV 有测），**Then** 可纠正漂移且不出现「计数偏低导致误删仍被引用版本」的验收失败。**现网**：生产路径尚未接线空闲 / 周期调度，留待后续迭代（不阻塞本迭代合并）。

## 约束与依赖

- 依赖并延续：`message-checkpoint-v2`（整树指针、回滚产品语义）、`vfs-revision-storage-optimize`（共享正文与同文短路合同）。  
- 建立在已落地的短路与批量预取行为之上，可将其内化进新热路径，而不是再单独验收一遍战术补丁。  
- Desktop / Mobile / CLI 共用 Core 语义；本迭代以 Core 行为与真机等待为主验收面。

## 非功能需求（业务/体验）

- 回滚确认后至成功提示之间，等待应缩短到用户可接受；本迭代不强制新增加载动画，但不得因架构改动引入更长的无反馈静默期。  
- 库体积可在「推迟内容块回收」窗口内短暂偏高，不得影响功能正确性。

## 风险与待确认项

- 引用计数与截断「同一版本被多个检查点引用」时的加减规则必须正确（按出现次数增减）；实现错误会导致误删或永不回收——以保守偏高 + `repairRefCounts` 空闲校验兜底（**API 已实现**；生产调度留后续 Step）。  
- 单事务脚本在移动端数据库绑定上的语句长度/多语句能力需在实现期验证；若受限，允许拆成同连接同事务内的极少次执行，但仍须远少于现网多阶段编排。  
- Path reconcile 在「锚点有直接检查点时是否删除目标树外 live 文件」存在历史文档与现网细微差异；本迭代**默认保持现网行为**，不借机改产品口径。  
- 检查点存储层 delta、PRAGMA 调优不在本迭代验收内，可记为后续增强。
